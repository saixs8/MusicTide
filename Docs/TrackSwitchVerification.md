# v0.3.1 切歌同步修复

2026-10-08。修改当前 v0.3.0 工程并发布到原 Output-Major 目录，保留菜单、放大歌名及播放／音量控制。

## 找到的问题

1. Process.MainWindowHandle/MainWindowTitle 在酷狗隐藏到托盘时为空。旧捕捉函数直接跳过该进程，导致真实时间线退回从零估算。现场所有酷狗进程 MainWindowTitle 为空，但原生窗口 265574 仍有当前歌曲标题。
2. 完整 UI Automation Descendants 扫描包含内嵌浏览器，托盘状态下探针长时间无法返回。切歌时清除时钟控件引用，又触发一次完整扫描，元数据和歌词更新跟着被阻塞。
3. 采集逻辑曾把窗口进度重新命名为系统会话标题。两个来源切歌更新不同步时，可能将上一首的位置、时长附到新歌名上。
4. 本地歌词文件列表扫描间隔 10 秒，新下载歌词可能延迟被发现；桌面歌词按文本跨缓存检索时，已知曲目仍可能匹配到其他歌曲。实际时长迟到时还会触发一次歌词清空。

## 修复

- EnumWindows 只读查找酷狗窗口，包括托盘隐藏窗口；原生歌曲标题与该窗口的时钟绑定。
- 优先从界面底部逐层找时间标签，找到即停止；缓存时间控件可跨同一窗口的切歌保留，每次仍核对所属歌曲。
- 一次后台时间读取尚未结束时，元数据轮询继续；时钟和 OCR 回退各只有一个在途任务，旧歌结果不用于新歌。
- 曲名先通知界面清理旧歌词；采集结束再核对歌曲身份，切歌过程中失效的一批结果直接丢弃。
- 曲名不匹配时不继承位置／时长。切歌立即刷新目录，缺失歌词每秒重试；桌面文本检索绑定已知曲目，未知曲目仍保留原有文本检索回退。
- 同一首歌补全时长时只更新时长与采样容量，保留歌词、播放时钟和资讯浏览状态。
